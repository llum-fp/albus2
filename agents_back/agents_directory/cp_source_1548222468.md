## Introduction

### What is a Captive Portal?
A captive portal is the web page/gatekeeper a user must pass (accept terms, authenticate) before being granted internet access on a network.

### Introduction to Scenic/Emerald Captive Portal

The **main functionality of the Captive Portal is to manage internet access and consumption for users** in both the crew and guest networks. Two authentication methods:

* **Authentication using PMS server (Cruisepal or MXP)** → Users authenticate through the captive portal using credentials stored locally in the PMS server. They use **cabin number, first name and last name**.
* **Authentication using Voucher (PMS Server NOT needed)** → Users authenticate using a **username and password** provided by reception or the Hotel Manager. The username/password combination is generated on Unity.

**NOTE:** The **MAIN** method Scenic/Emerald want to use is **Authentication using PMS server**. Vouchers are an **alternative**, used for example:
* When PMS Server fails.
* When a guest struggles to connect using the PMS Server method (provide a voucher while troubleshooting).
* Hotel Manager (or other Scenic/Emerald personnel) requests.

So the voucher is an alternative method that can be used **to avoid bypassing the Captive Portal**.

The Captive Portal is also used to **collect guest email information**. Scenic/Emerald uses these to send guests Satisfaction Surveys after the cruise — a key service for them. The **Hotel Manager has a web interface** to access and collect the emails.

### Service Restrictions

* Each user must connect to the **SSID corresponding to their group**, otherwise access will not work. A crew member on the guest portal (or a guest on the crew portal) will have credentials that do not work.
* To gain internet access during the initial login, **the user (crew or guest) must have an active account in the PMS server (Cruisepal or MXP)**. If a user's account has expired (current date is past the account's end date in the PMS server), they can no longer log in. The hotel manager must recreate the user account in the PMS server to restore access.

### Description of elements involved

* **Fortigate:** The main **networking** part. Allows/denies traffic between parts, routes Guest and Crew traffic to Ucopia when the CP is enabled, provides final access to the WANs. Defines which applications are allowed, SD-WAN rules, application recognition, and traffic shaping per network.
* **Ucopia:** A **controller software** that defines different policies per access network and applies different profiles per user. Manages **quotas per user** and applies restrictions once quotas are expired. Manages **validity of users** (removes a user once no longer valid). Also acts as **DHCP server** for guest and crew networks.
* **Captive portal host:** A **Linux Debian server** hosting the captive portal. Hosts all CP code and configuration and runs the logic to authenticate users — the **brain of the system**. It checks credential validity, creates/updates users on Ucopia, modifies passwords, and stores all information in the Database.
  * **Captive portal database** (on the same Debian server). Two main functions:
    * **Store all information** from Clients, devices, and survey emails when users connect. Used to apply logic (e.g., remove users when expired) and show information in Unity Local Admin and the Hotel Manager web (to retrieve emails).
    * **Configuration tables** — the main point of CP configuration and personalization (e.g., IP range allowed per network, view package to use (Viking, Scenic, Emerald…), type of logs to display).
* **Mikrotik:** The router on the customer's internal network side. Their required config is a **DHCP Relay** on Guest and Crew interfaces pointing to our FG IP in the Transit VLAN (`10.254.199.1`).
* **PMS server (Cruisepal or MXP):** Property Management System. Stores the guest and crew information.
  * Scenic/Emerald **River** Cruises → **CruisePAL** (managed by a third-party vendor).
  * Scenic/Emerald **Ocean** Cruises → **MXP** (managed by a third-party vendor).

### Unity Local Admin
A dashboard in Unity intended as a **point of visibility and control of the Captive Portal**. Requires at least **Unity version 4.1.8** to install the Local Admin.

## Captive Portal flows

### End user flow — Guest using PMS server (Cruisepal or MXP)
1. Guest goes to reception and checks in. The receptionist/hotel manager enters his data into the **PMS server**. Once registered in PMS, he can register on the captive portal.
2. Guest connects his first device to the **Guests Wi-Fi SSID**. It first negotiates an IP with Ucopia:
   1. Mikrotik receives the DHCP request and forwards it to Fortigate via DHCP relay. Fortigate forwards it to Ucopia (the DHCP server).
   2. Ucopia replies to the DHCP request.
3. The client tries to use the internet via any application.
4. Through any DNS request from the client to the Internet, Ucopia intercepts the request.
5. Ucopia checks if the device MAC is already assigned to a user.
6. **If MAC is NOT stored (new user):**
   1. Replies with a "moved temporarily" message to the captive portal URL.
   2. The client tries to reach the URL and must resolve it to an IP.
   3. Sends a DNS request to the device's default DNS (obtained via DHCP).
   4. Receives the DNS response resolving the captive portal IP.
   5. The browser loads the captive portal welcome screen (Scenic or Emerald view depending on vessel).
   6. The guest accepts Terms and Policies and clicks Continue. The registration form appears. The guest must fill it with the data entered in the PMS server.

   **IMPORTANT WARNING!** Example guest "Esteban Ivan Krumrick": Firstname=Esteban, Middlename=Ivan, Lastname=Krumrick. If in PMS Server the receptionist configured Firstname="Esteban Ivan" and Lastname="Krumrick", then the guest must enter "Esteban Ivan" in the Firstname field of the registration form, otherwise an error pops up.

   g. After entering proper credentials, data is checked against the PMS server. If it matches, the **Guest Satisfaction Survey** screen is shown, where guests enter their email and can check the Marketing preferences checkbox.

   i. After entering email and clicking Next, Client/Device/Survey data is written to the Captive Portal Database.

   j. Captive portal validates the information depending on stage and status:
   * **Registration:** searches user in PMS Server; if valid, creates a new user in Ucopia, enables the user session in Ucopia, and logs each action to the DB.
   * **Login:** searches user in PMS Server; if still present, enables the user session in Ucopia and logs to the DB.

   k. On success, the browser is redirected to the "Connected to Internet" screen, showing: 1) connection details, 2) a link to edit settings in the Survey screen, 3) a button to refresh data.

   l. The user can now browse the internet.
7. **If MAC IS already assigned to a user:** The user is automatically enabled for internet (provided the number of simultaneously connected MAC devices and the total simultaneous sessions have not reached their maximums). Through `cp.sailwifi.com` users can access the portal and see internet status.
8. Users navigate the internet; services are managed per the defined profile.

### End user flow — Crew using PMS server (Cruisepal or MXP)
Exactly the same as for Guest, EXCEPT crew members are **not** prompted with the "Guest Satisfaction Survey" screen and are not asked for their email.

### End user flow — Guest and Crew using Voucher
1. With this method the user does **not** need to be registered in PMS Server.
2. The user connects to the proper Wi-Fi SSID and negotiates an IP with Ucopia (same DHCP relay path as above).
3–5. Same DNS interception / MAC check as the PMS flow.
6. **If MAC is NOT stored (new user):**
   1–5. Same captive-portal redirect and welcome screen as above.
   6. The user accepts Terms and Policies and clicks Continue.
   7. The user clicks the **"Login via Voucher"** link; the form changes to ask only username and password.
   8. The user enters a voucher username and password.
   9. The Captive Portal checks against the CP Database for an existing username/password combination matching the entered values.
      * **Registration:** if valid, creates a new user in Ucopia, enables the session, and logs to the DB.
      * **Login:** enables the session in Ucopia and logs to the DB.
   10. On success, the browser is redirected to the "Connected to Internet" screen.
7. **If MAC IS already assigned:** automatically enabled (subject to device/session limits). Through `wifiaccess.co` users can access the portal and see internet status.
8. Users navigate the internet; services managed per profile.

### Device limit reached
If a user tries to connect a device but has reached his allowed device limit, after completing the register form an intermediate screen is shown to **disconnect one device** out of the Captive Portal.

### The invisible flow of deprecated users
Users created in DB and Ucopia both have an expiration date.
* In **Ucopia**, the user is cleared the **day after** the expiration date.
* In the **Captive Portal database**, the user is cleared by an internal process once the expiration date has passed. This appears in the CP logs near 12 AM each day, e.g.:
```
<200>1 2026-03-11T00:00:01Z localhost script-cp INFO Cronjob delete-outdated-client started
<200>1 2026-03-11T00:00:01Z localhost script-cp INFO Syncing PMS data
<200>1 2026-03-11T00:45:01Z localhost script-cp INFO Cronjob remove-expired-devices started
```

### VRF Loop explanation
Incoming internet traffic from the Crew and Guest networks, arriving from the Transit to the Mikrotik interface, is sent to Ucopia via the **uc_in** interface using an SD-WAN rule on Fortigate (**CPEnablerCrew** or **CPEnablerGuest**). Ucopia applies the necessary quotas and rate limits, then forwards traffic to **VRF 30** via its WAN interface. This traffic enters VRF 30 through the **uc_out** interface and is routed to **VRF 0** via **transit2vrf_0**.

A **NAT** is applied to this outgoing traffic as it leaves interface **transit2vrf_0** to prevent routing conflicts — without it, traffic would enter the Fortigate with the same source IP via two different interfaces within the same VRF.

Finally, Fortigate applies firewall policies and SD-WAN definitions to route the traffic. If permitted, traffic is forwarded to the internet.

**VRF Loop — L3 routes:** SD-WAN rules direct internet traffic to Ucopia. In the VRF30 routing table, the **uc_out** interface is the gateway to reach the Guest and Crew networks, ensuring traffic from these networks satisfies the **RPC (Reverse Path Check)** on Fortigate and avoids being dropped. A NAT is applied to traffic passing through VRF30 — the same Crew/Guest traffic is sent to VRF0 with a different source IP to prevent routing conflicts. Static routes are added to VRF0 to reach the NAT IPs, ensuring incoming traffic via Transit2vrf_30 satisfies the RPC and is not dropped.

## Configuration

### Fortigate
Two clear parts:
* **The Captive Portal setup itself** → communication between the CP, Ucopia, and Fortigate.
* **The LANs to work over the Captive Portal** → having traffic from a LAN (Guest, Crew) routed over Ucopia.

**WARNING** → Scenic/Emerald Ocean vessels have different IPs (CP interfaces `10.255.X.X` instead of `10.245.X.X`; Guest/Crew ranges ad-hoc).

**Captive Portal Setup includes:**
* Interfaces → **uc_in** is created as a WAN interface.
* Address objects (note: PMS Server / Cruisepal IP differs between vessels).
* SD-WAN zone → uc_in must be an SD-WAN zone member to be used in SD-WAN rules.
* FW Policies.
* Central SNAT.
* DNAT → configured to NAT the internal IPs of Ucopia and CP to IPs in VLAN 222 (System).
* Static Routes.
* SD-WAN Rules → adding **uc_out** to MGMT→ALL SDWAN.

**LAN to work over Captive Portal** (in Scenic only 2 LANs — Guest and Crew):
* DHCP relay on the proper interface → in Scenic, **Fusion_Transit**. All DHCP requests on this interface are forwarded to `10.254.149.1` (Ucopia).
* Address objects, IP Pools, Static routes, Central SNAT.
* SD-WAN Rules → these are what enable traffic to flow to Ucopia.

### Ucopia
**WARNING** → Scenic/Emerald Ocean vessels have different IPs (as above).

**Network:**
* Controller name and domain name.
* Incoming networks (Guest, Crew).
* Outgoing networks.
* Static Routes (routes related to Guest/Crew traffic are the relevant ones).
* DNS Server.

**Other important configuration:**
* Certificates → `*.sailwifi.com` as the default certificate.
* Portals.

### Captive Portal host
**WARNING** → This section is informative, to understand CP host config. These settings must not be edited under any circumstance.

* **/etc/hosts** → system file for local hostname resolution; maps hostnames to IP addresses without querying external DNS. **WARNING** → Scenic/Emerald Ocean Cruises have MXP addresses (not Cruisepal) that differ per vessel (e.g., Kaia → `kaiamxpia.kaia.internal`).
* **/var/www/html** → In a Laravel deployment, the root directory where the application is installed (framework, config, dependencies, source code).
* **/var/www/html/.env** → configuration file defining environment variables (credentials, API keys, DB parameters, app settings) outside the source code. Most important parameters to check:
  1. **RESCO URL** → Cruisepal URL defined in /etc/hosts (**MXP_URL** in Oceans).
  2. **APP URL** → the Captive Portal URL (the one users use to authenticate).
  3. **CONTROLLER URL** → Ucopia controller URL.
  4. **UCOPIA URL** → Ucopia API URL.
  5. **Unity IP** in **ADMIN_API_WHITELIST**.
* **/var/www/html/storage/logs/** → the **most important folder for troubleshooting**; stores Captive Portal logs (usage logs and Laravel logs). Tier 1 and Tier 2 usually only need the **usage logs** (normal CP usage: registers, logins, deleting users…). **Laravel logs** are checked when an application bug or unexpected behavior is suspected — usually caused by an unexpected response from the PMS server (bad field format…).
* **/var/www/html/VERSION** → the current version of the CP.
* **/home/omniaccess/RESCO_scripts** → Python scripts to print information stored in the PMS server (Cruisepal). See the PMS Server section for usage.

### Captive Portal Database
Hosted on the same Linux Debian server. Many tables, but only some are relevant for Scenic/Emerald. Two main functions: store client/device/survey info, and configuration tables.

**Configuration tables (edited via Rundeck):**

**portal_configs** — main CP configuration; only a few parameters are editable:
| Field | Description |
| --- | --- |
| kick devices on pin reset | When PIN is reset, disconnect all devices associated to the account. **Scenic DO NOT use PIN.** |

| Field | Description |
| --- | --- |

**role_features:**
| Field | Description |

## Log visualization

### Ucopia
Ucopia logs are only viewable via SSH. The main command is **`showLogs`**, with filters:
```
showLogs [type] [-n number] [-d day]
  type     Word to search (e.g. radius, dhcp) or a pattern
  -n number  Search in the last 'number' log events [default 1000]
  -d day     Search a specific day (0=today, 1=yesterday, range x-y; a day starts at 6:25 AM) [0]
```
There are different log levels; current settings suffice for most troubleshooting. Contact Ucopia support for deeper debug levels.

**Example 1 — Filter by date:** to filter for today (13-Mar) starting at 06:00:
`showLogs -n 1000000 "13 06:00"`
**NOTE** → use a very large number of lines (at least 1000000) so Ucopia actually prints the logs. Example log lines show AutoConnect reloads, quota checks (`isQuotaApplicable`), user connect (`ACCEPT`), forced disconnects when `forceDisconnectTimer` expires, etc.

**Example 2 — Filter by type:** to filter logs containing the word DHCP:
`showLogs dhcp`
Example output shows `DHCPDISCOVER` / `DHCPOFFER` / `DHCPREQUEST` / `DHCPACK` lines with IP, MAC, and device name.

### CP host
* **Using Rundeck scripts to gather logs by room:** A Rundeck job (project OA_Services → CaptivePortal/SolutionsArchitect/Logs) returns the users present in a room with their CP-database information and the raw logs related to those users. Scrolling down shows the same logs formatted in a user-friendly way (numbered, with unimportant headers removed).
* **Raw log files:** Accessed via SSH or WinSCP, located in **`/var/www/html/storage/logs/`**. A new file is created each day. Logs show user registration attempts, API calls to Ucopia to create accounts, users not present in the PMS server, incorrect input data, and failed/successful connections.
* **Real-time logs:** Best option for real-time troubleshooting — access the CP host and tail the logs. To print the last 50 lines and follow in real time:
  `tail -f -n 50 /var/www/html/storage/logs/usage-2026-03-13.log`

## Troubleshooting
Refer to the dedicated Troubleshooting folder and the Work Instructions folder in the CP Confluence space for troubleshooting options, tools, and step-by-step instructions.

Common troubleshooting touch-points implied by the guide:
* User cannot register/login → confirm the user exists and is active (not expired) in the PMS server (Cruisepal/MXP); for MXP, **checkedIn must be True**.
* Name mismatch → the Firstname/Lastname entered on the form must exactly match the PMS server fields (including multi-word first names).
* Wrong SSID → user must connect to the SSID for their group (Guest vs Crew).
* Device limit reached → disconnect a device via the intermediate screen; remember the real device limit is the `num_of_devices` in the CP database **profiles** table (Ucopia multidevice must be ≥ that value).
* Duplicated user in Cruisepal → report to Cruisepal; authentication uses the unique **account_id**.
* PMS Server down → use vouchers as a temporary alternative.
* Check usage logs (`/var/www/html/storage/logs/`) for normal events; check Laravel logs for suspected application bugs / bad PMS responses.
* Ucopia: use the **Accounts** tab to confirm a user registered, **Sessions** to see auth type/duration, **DHCP leases** for IP↔MAC mapping, and `showLogs` over SSH for DHCP/auth events.
