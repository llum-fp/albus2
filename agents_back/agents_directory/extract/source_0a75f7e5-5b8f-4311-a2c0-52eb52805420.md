# Building AI Cartels

A practical orientation for engineers about to build on the AI Hub platform. This
page is the entry point: it covers what a cartel is, when you'd build one, which
type fits the work in front of you, and which page to read next. Code-level
walkthroughs live in the two child pages — **MCP Cartel** (`./mcp-cartel.md`) and
**AI-Core** (`./ai-core.md`) — and the in-repo `docs/` directory.

> ⚠️ **IMPORTANT — Before you start.** This page builds on top of the base Python
> cartel concept — the `mesh_core.Service` class, the cartel lifecycle, commands,
> and periodic tasks. The canonical reference is **Cartels - Python** (page link
> to space key `PLA`, content title "Cartels - Python", version-at-save 33) in the
> PLA space. Read it first if you haven't built a cartel before; the rest of this
> page assumes that foundation.

## 1. What is a cartel?

A **cartel** is a long-running Python service that plugs into the AI Hub platform.
The platform handles the infrastructure plumbing (command bus, authentication,
observability, model routing); a cartel is where your team's domain logic lives.

Two things every cartel has in common:

- It registers with the platform's command bus (RabbitMQ via `mesh_core`) and is
  reachable as a named service. Other cartels and the platform CLI can call it by
  name.
- It runs as its own deployable unit — its own container, its own logs, its own
  quota and audit trail.

What varies is the cartel's *purpose*. Some cartels exist to **expose an external
system as tools** that other cartels' agents can call — a Fortigate cartel lets
agents query firewall state, a Proxmox cartel exposes hypervisor operations, an
Alanis cartel surfaces fleet telemetry. Other cartels exist to **consume those
tools** — running agents and workflows that combine LLM reasoning with the tool
catalog to make domain decisions and emit events for downstream services.

The platform supports both roles, and a single cartel can play one, the other, or
both. The next section walks through how to choose.

---

## 2. Which kind of cartel do I want?

A cartel has two **surfaces** — places where it interacts with the platform — and
your cartel uses one, the other, or both:

- **Publish.** Expose capabilities your team owns (an external system, a domain
  operation) as tools that agents in other cartels can call.
- **Consume.** Run agents and workflows that call tools from the platform's
  catalog and use LLMs to make decisions.

Three shapes follow from those two surfaces:

| Shape | Surfaces | You import | Reference cartels |
|---|---|---|---|
| **MCP cartel** | publish | `mcp-cartel` | `cartels/alanis`, `cartels/fortigate`, `cartels/proxmox`, `cartels/freshdesk` |
| **AI cartel** | consume | `ai-core` (which already pulls `mcp-cartel` underneath, but the publishing surface stays unused) | `cartels/anomaly-detection`, `cartels/remediation-cartel` |
| **Hybrid** | publish + consume | `ai-core` (both surfaces used in the same service) | None currently — the shape is supported but no production cartel exercises it yet. |

### How to pick

**MCP cartel** is the right shape when your team owns a system — a SaaS API, a
network device, a domain service — and other teams want to write AI workflows that
call into it. You ship a service that wraps your system's operations as tools,
registers them with the platform, and stops there. You don't import `ai-core` and
you don't run agents yourself. → **MCP Cartel** (`./mcp-cartel.md`).

**AI cartel** is the right shape when you're building an AI workflow that combines
tools other teams publish with LLM reasoning to make decisions or react to events.
You don't expose anything new — your cartel only calls the catalog, not contributes
to it. → **AI-Core** (`./ai-core.md`).

**Hybrid** is the right shape when your AI workflow consumes a system that only
your team owns *and* those same capabilities should be available for other teams to
use independently. Rather than split into two cartels, one service uses both
surfaces. The platform supports this — `ai-core` already pulls in the publishing
machinery — but no production cartel does it today, so the first team to ship a
hybrid will be validating the shape end-to-end. → both child pages; start with
**MCP Cartel** (`./mcp-cartel.md`) to register your tools, then **AI-Core**
(`./ai-core.md`) for the AI side.

## 3. What the platform handles vs what you write

The platform takes care of plumbing so cartel code stays focused on domain logic.
The split below is the same regardless of cartel shape — pick the surface(s) your
cartel uses. The *how* for each item in the "You write" column lives in the child
pages and the in-repo docs.

### Publish surface

| Handled by the platform | You write |
|---|---|
| RabbitMQ command routing — each registered tool is reachable as a named RPC handler. | The tool function (an async Python function) and its input/output schema. |
| Tool registration with the Gateway catalog so AI cartels discover your tools through `GET /v1/tools`. | The service class that declares the tools it publishes. |
| Authentication on incoming calls — the Gateway validates the caller's JWT and propagates project/user identity before your function runs. | Domain authorization *inside* the tool when behavior depends on caller identity (e.g. "this user can only read fleet X"). |
| Per-call audit — every invocation is recorded with caller, args, duration, and outcome in the Gateway's audit tables. | Domain-level events you want surfaced beyond audit (logs from your external system, custom metrics). |
| Container build, secret distribution, OTel traces / metrics / logs. | The `Dockerfile`, `pyproject.toml`, and the env vars for credentials your external system needs. |

### Consume surface

| Handled by the platform | You write |
|---|---|
| Gateway client wired from env — `self.gateway.tools.*` and `self.gateway.llm.*` are available with auth, circuit breaker, and audit already attached. | Activity code that calls into the Gateway. |
| LLM model resolution — `self.llm_models["light"]` and `self.llm_models["advanced"]` are routed through the Gateway, no provider names anywhere in your code. | Which tier to use per workflow phase, and the prompt content. |
| Temporal worker, auto-started from `workflows` and `activity_classes` declared as class attributes. | The workflow classes (`@workflow.defn`) and activity classes (`CartelActivities` subclasses). |
| Agent factory — `build_agent_with_tools(...)` fetches the Gateway's tool catalog and registers each tool as a typed PydanticAI function. | Which skills to compose, which tools to allowlist, what structured output type to extract. |
| Audit pipeline — `AuditHook` is auto-prepended so OTel spans carry canonical `ai.session.*` / `ai.tool.*` attributes joinable with Gateway spans by `trace_id`. | Stamping the span at each phase boundary via `GovernanceContext.set_session(...)`. |
| Skills loader, mesh_core extras (commands, periodic tasks, event publish/subscribe, ORM proxy). | Domain-specific commands, periodic-task cadences, event payloads, and (if your cartel owns tables) ORM models. |
| Per-cartel schema isolation when your cartel owns tables — Postgres schema creation, sibling migrator service, `search_path` bootstrap. | YAML model definitions in `models/`, Alembic migrations in `migrations/`, and the cartel's `Makefile` hooks. |

A hybrid cartel uses both tables; mesh_core infrastructure (commands, events, ORM,
observability) is shared underneath, so you don't pay for it twice.
